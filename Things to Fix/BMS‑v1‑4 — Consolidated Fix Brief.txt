## P0 — Correctness (actively wrong now)

### TASK‑1 (High): AR/void journal posts one‑sided reversals
**Files:** `repo/ArPaymentRepository.java` (`findForJournal`), `svc/GlService.java` (`postVoidTenderSplit`, `postVoidReversal`, `postArPayments`).
**Anchor:** `AND p.reversedAt IS NULL` (inside `findForJournal`); `case CREDIT -> GlMapping.EventType.TENDER_CLEARING;`.
**Problem:** `findForJournal` excludes reversed payments, so a reversed AR payment loses its collection entry while `findReversedForJournal` still posts the reversal → AR inflated, cash understated. The round‑4 `postVoidTenderSplit` (CREDIT→TENDER_CLEARING) made it worse. Verified: credit sale 100 + AR cash 100 + void currently nets **AR +200 / CASH −100 / TC −100** (should be all 0).
**Fix (complete model):**
1. `findForJournal`: delete `AND p.reversedAt IS NULL` (always post the collection at `paymentDate`).
2. `postArPayments`: skip the `ARP‑REV` reversal entry when `payment.getInvoice().getIsVoided()` is true (the void reversal handles it).
3. `postVoidReversal`: replace the single tender leg with the same netting `SaleService.voidSale` uses — credit **AR** for the still‑outstanding portion, **CASH** for net cash refunded (`cashCollected − priorRefunds`), **REFUND_LIABILITY** for net non‑cash converted; keep revenue/tax/COGS net of returns. Remove `postVoidTenderSplit`.
**Verify (journal nets):** paid+void → AR 0/CASH 0/REV 0; paid+return 30+void → AR 0/CASH 0/REV 0; unpaid credit void → AR 0/REV 0; partial‑paid 40+return 30(debt)+void → AR 0/CASH 0/REV 0.
**Test:** build these four scenarios, assert per‑account debit−credit nets.

### TASK‑2 (Medium): Write‑off return double‑counts outflow in movement stats
**Files:** `svc/SaleReturnService.java` (write‑off branch), `svc/InventoryService.java` (`getMovementStats`), `repo/StockMovementRepository.java` (`findMovementsSince`).
**Anchor:** `loss.setReasonCode("RETURN_WRITE_OFF");`; `boolean isIn = type == StockMovement.MovementType.IN`.
**Problem:** Round‑4 re‑added the write‑off `ADJUSTMENT_OUT` movement (good for traceability) but `getMovementStats` counts it as outflow, though the units already left at sale time → `totalOut`/`netChange` inflated (regression of a round‑3 fix).
**Fix:** add `reasonCode` to the `findMovementsSince` projection; in `getMovementStats` skip rows with `reasonCode = "RETURN_WRITE_OFF"` from the IN/OUT accumulation. (Stock/ledger are already correct — stats only.)
**Test:** sale 5 + write‑off return 5 → `totalOut` reflects 5 (the sale), not 10.

## P1 — Functional bugs

### TASK‑5 (Medium): Fully‑discounted (zero‑total) order can't be converted
**File:** `svc/SaleService.java` (`createSaleFromOrder`).
**Anchor:** `Amount paid is required and must be positive`; `paymentLine.setAmount(totalAmount);`.
**Problem:** Round‑4 zero‑total fix only patched `createSale`. Conversion still requires `amountPaid > 0` and builds a 0‑amount payment line → `verifyForSale` rejects.
**Fix:** mirror `createSale`: when `totalAmount.signum() == 0`, skip the amountPaid guard and payment validation, set `paymentMethod=CASH`, `amountPaid=0`, `changeGiven=0`, `paymentLines=List.of()`.
**Test:** order with 100% shop discount (total 0) converts successfully; stock deducted; no payment rows.

### TASK‑6 (Medium): Two inventory‑value reports disagree
**File:** `svc/ReportService.java` (`getInventoryReport`).
**Anchor:** `int stock = product.getStockQuantity() == null ? 0 : product.getStockQuantity();`.
**Problem:** Values shop stock only; `InventoryService.getSummary` values all owned stock (round‑3 BUG‑4 missed this path).
**Fix:** use `locationService.totalOwnedUnits(product)` (inject `LocationService`) for the unit count/valuation so it matches `getInventoryValues`.
**Test:** product with 5 shop + 7 backroom → both reports value 12 units.

### TASK‑7 (Medium): Order below‑cost check ignores the header discount
**Files:** `svc/OrderService.java` (`createOrder`), `svc/SaleService.java` (`createSaleFromOrder`).
**Anchor:** `effectiveUnitPrice.compareTo(lineCost) < 0`; `linePrice.compareTo(lineCost) < 0`.
**Problem:** Both check the pre‑header‑discount unit price; direct sales check the allocated net price (`assertNetPriceRespectsCostPolicy`). A discounted order can sell below cost without the manager gate.
**Fix:** allocate the header discount to lines (reuse `SaleDiscountUtils.allocateDiscounts` logic) and compare the **net** unit price vs cost, exactly like `createSale`.
**Test:** REQUIRE_MANAGER policy + shop discount that pushes a line below cost → cashier order create/convert throws; manager passes.
