Four parts. Read Part 4 first if you only have time for one thing today — it's a confirmed, 31-occurrence bug across 17 files, and it's very likely the actual explanation for the "some pages don't update" problem you're describing.

## PART 1 — Production Schema Management (Flyway — zero manual SQL, ever again)

### Why this, not another schema.sql you run by hand

You've hit the same problem repeatedly in this project: `ddl-auto` flips between `update`/`validate`, migrations get given as manual `ALTER TABLE` statements that are easy to forget or run out of order, and there's no record of what's actually been applied to your real database versus what's just described in a document somewhere. **Flyway solves this properly** — it's the standard production tool for exactly this problem. You still write SQL (there's no way around that for a SQL database), but you never *run* it — you drop a numbered file into a folder, and Spring Boot automatically applies any new one on the next startup, in order, and remembers exactly what's already been applied in a tracking table so it never re-runs or skips anything. This is the actual production-grade answer to "I don't want to execute any SQL queries."

### Step 1 — Add the dependency

**File: `bms-backend/pom.xml`** — add inside `<dependencies>`:
```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-mysql</artifactId>
</dependency>
```

### Step 2 — Configuration

**File: `bms-backend/src/main/resources/application.yml`** — change `ddl-auto` and add Flyway config:
```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate   # Hibernate only checks the schema matches entities — never changes it
  flyway:
    enabled: true
    baseline-on-migrate: true
    locations: classpath:db/migration
```
From now on, **Flyway is the only thing that ever changes your database structure.** Hibernate's `validate` will actually help you here too — if an entity and the real schema ever disagree, the app refuses to start with a clear error, instead of silently running with a mismatched schema.

### Step 3 — The baseline migration (your full current schema, as Flyway's starting point)

**New file: `bms-backend/src/main/resources/db/migration/V1__baseline_schema.sql`**

This is generated by reading every entity class directly, same as the schema regeneration done earlier in this project — every table, column, index, and enum matches your actual current `.java` entity files, including everything added since (Refund/RefundItem, ShopInfo, Expense, CashShift, the `unit` column, `customer_display_name`, `cost_price_at_sale`, `quantity_refunded`, the nullable `supplier_id`, and the `version` columns from the optimistic-locking fix). Put the full schema from the earlier regeneration into this file, with these specific updates layered in:

```sql
-- (Full schema as previously regenerated — roles, users, categories, products,
--  product_images, suppliers, customers, purchases, purchase_items, sales,
--  sale_items, refunds, refund_items, stock_movements, system_settings,
--  audit_logs, shop_info, expenses, cash_shifts — plus everything below)

-- Additions since the last full regeneration:
ALTER TABLE products ADD COLUMN unit VARCHAR(20) NULL;

ALTER TABLE sale_items ADD COLUMN quantity_refunded INT NOT NULL DEFAULT 0;

-- Optimistic locking (Part 1 of the worst-case audit fixes)
ALTER TABLE products ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
ALTER TABLE categories ADD COLUMN version BIGINT NOT NULL DEFAULT 0;
ALTER TABLE suppliers ADD COLUMN version BIGINT NOT NULL DEFAULT 0;

    changed_by BIGINT NOT NULL,
    changed_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

-- Currency setting (Part 2 of this document)
```

**If you already have a real database with data in it right now:** Flyway's `baseline-on-migrate: true` handles this cleanly — on first run, it records your *current* database state as the baseline without trying to re-run `V1` against tables that already exist, then only applies anything genuinely new from that point forward. You don't need to drop and recreate anything.

### Step 4 — The workflow going forward

Every future schema change becomes a new file: `V2__add_something.sql`, `V3__another_change.sql`, numbered in order, placed in the same `db/migration` folder. Spring Boot applies each pending one automatically the next time it starts — you write the file, commit it, restart the app, done. You will never again need to manually connect to MySQL and type an `ALTER TABLE` statement yourself, and there's now a permanent, ordered record (in Flyway's own `flyway_schema_history` table) of exactly what's been applied and when.

## PART 2 — Currency Picker in Settings

### The real scope here

Currency formatting isn't done in one place — I checked, and it's independently duplicated in **6 different files** (`utils/helpers.js`, `POS.jsx`, `Dashboard.jsx`, `ShiftHistory.jsx`, `FinancialSummaryCards.jsx`, and one more), every one hardcoded to `'en-US'`/`'USD'`. Adding a currency picker properly means consolidating these into one source of truth first — otherwise you'd change the setting and only 1 of 6 places on screen would actually reflect it.

### Backend

`system_settings` already has a `currency_symbol` key (`'$'`) — but nothing reads it, and a bare symbol isn't enough to drive `Intl.NumberFormat` correctly (that needs a real ISO currency code like `USD`/`EUR`/`THB` to get correct decimal places, symbol placement, and grouping per-currency). Use the `currency_code` setting added in Part 1's migration instead, and treat `currency_symbol` as legacy/unused going forward (safe to leave in place, just stop relying on it).

**Endpoint already exists** (`GET /api/settings/key/{key}`, per earlier work — Admin and Manager can both read it) — no new backend endpoint needed, just make sure `PUT /api/settings/{id}` (or whatever the existing update-setting endpoint is) works for this key like any other setting.

### Frontend — one shared currency-aware formatter

**File: `frontend/src/utils/helpers.js`** — find the existing `formatCurrency` and replace it with a version that reads the live setting:

```js
import { systemSettingService } from '../api/services';

let cachedCurrencyCode = 'USD'; // sensible default before the real setting loads

export const setCurrencyCode = (code) => { cachedCurrencyCode = code || 'USD'; };

export const formatCurrency = (amount) => {
  try {
    return new Intl.NumberFormat(undefined, {
      style: 'currency',
      currency: cachedCurrencyCode,
    }).format(amount || 0);
  } catch {
    // Invalid/unsupported currency code — fail safe rather than crash the page
    return new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).format(amount || 0);
  }
};
```
(`Intl.NumberFormat(undefined, ...)` — passing `undefined` as the locale uses the browser's own locale for number grouping/decimal conventions, while still using whatever currency code you set. This is a nicer default than hardcoding `'en-US'` regardless of who's actually using the app.)

**New file or addition to `App.jsx`** — load the real setting once, early, and keep it in sync:
```js
// Near the top-level app setup, run once on load
systemSettingService.getByKey('currency_code').then((res) => {
  if (res?.data?.settingValue) setCurrencyCode(res.data.settingValue);
});
```

**Now delete the 5 duplicate local `formatCurrency` functions** in `POS.jsx`, `Dashboard.jsx`, `ShiftHistory.jsx`, `FinancialSummaryCards.jsx`, and the fifth file found — replace each with:
```js
import { formatCurrency } from '../utils/helpers';
```
This is the real fix — a currency picker only means something once every screen is actually pulling from the same place.

### Settings page

**File: `frontend/src/pages/Settings.jsx`** — add a Currency selector:
```jsx
const CURRENCIES = [
  { code: 'USD', label: 'US Dollar ($)' },
  { code: 'EUR', label: 'Euro (€)' },
  { code: 'GBP', label: 'British Pound (£)' },

  { code: 'MMK', label: 'Myanmar Kyat (K)' },
  { code: 'SGD', label: 'Singapore Dollar (S$)' },
  { code: 'INR', label: 'Indian Rupee (₹)' },
  // add whichever currencies actually matter for your target markets

<TextField select label="Currency" value={currencyCode} onChange={handleCurrencyChange} fullWidth sx={{ mb: 2 }}>
  {CURRENCIES.map((c) => <MenuItem key={c.code} value={c.code}>{c.label}</MenuItem>)}

```
On save, call the existing setting-update endpoint for the `currency_code` key, then also call `setCurrencyCode(newCode)` immediately (from the helper above) so the change reflects across the app right away, without needing a full page reload.

### Acceptance criteria
- Changing the currency in Settings updates every dollar amount across the entire app (Dashboard, POS, receipts, Accounting, Analytics) — not just some of them.
- An unsupported/invalid currency code doesn't crash the app — falls back to USD formatting cleanly.

## PART 3 — Responsive Table Columns for Mobile

### The pattern to apply everywhere

MUI's `sx` prop supports responsive breakpoint objects directly — hide a column below a given screen width by setting `display: { xs: 'none', sm: 'table-cell' }` on both the header `<TableCell>` and every corresponding body `<TableCell>` in that column. Apply this consistently: **keep the columns that answer "what is it and how much," hide the columns that are secondary/drill-down info** on narrow screens.

### Example — `Products.jsx`

**Find each of these header cells and add the responsive `sx`:**
```jsx
<TableCell sx={{ display: { xs: 'none', md: 'table-cell' } }}>Category</TableCell>
<TableCell align="right" sx={{ display: { xs: 'none', sm: 'table-cell' } }}>Threshold</TableCell>
```
**And the matching body cells in the same row:**
```jsx
<TableCell sx={{ display: { xs: 'none', md: 'table-cell' } }}>{product.categoryName || '-'}</TableCell>
<TableCell align="right" sx={{ display: { xs: 'none', sm: 'table-cell' } }}>{product.minStockLevel || 10}</TableCell>
```
Keep visible at every width: Image, Name, Price, Stock, Status, Actions — everything else (SKU, Category, Threshold) can hide progressively as the screen narrows.

### Apply the same pattern to your other data-heavy tables
`Sales.jsx`, `Customers.jsx`, `Suppliers.jsx`, `Purchases.jsx`, `ShiftHistory.jsx` — same approach, same principle: keep the 3-4 columns that identify the row and its headline number, hide supporting detail columns below `sm`/`md`. Since this is the same mechanical change repeated across several files rather than one piece of novel logic, apply it file-by-file using this exact pattern rather than needing a different approach per page.

### Acceptance criteria
- On a phone-width viewport, every major list page shows a clean, readable table with no horizontal scrolling required and no columns crushed unreadably small.
- On desktop width, nothing changes — all columns still show exactly as they do today.

## PART 4 — App-Wide Reactive Data Fix (the big one)

### Confirmed root cause

I searched the whole frontend: **31 occurrences of `invalidateQueries([...])` (the broken v4-style bare array) across 17 files**, versus only 6 using the correct v5 object form (`invalidateQueries({ queryKey: [...] })`). This is almost certainly the actual explanation for "some pages update, some don't" — it was never that some pages *implemented* the reactive pattern and others didn't; nearly every page *attempted* it, but most of them are calling the API in a shape that TanStack Query v5 doesn't recognize as intended, since this project is plain JavaScript and nothing catches this at compile time.

### Every affected file

```
pages/ProductForm.jsx
pages/BackupSettings.jsx
pages/Accounting.jsx
pages/Sales.jsx
pages/CustomerForm.jsx
pages/CategoryForm.jsx
pages/POS.jsx
pages/PurchaseForm.jsx
pages/Users.jsx
pages/Customers.jsx
pages/Products.jsx
pages/Suppliers.jsx
pages/Settings.jsx
pages/StockAdjustment.jsx
pages/SupplierForm.jsx
pages/Purchases.jsx
pages/ShopInfo.jsx
```

### The fix — mechanical, apply to every occurrence in every file above

**Find every instance of this shape:**
```js
queryClient.invalidateQueries(['someKey']);
```
**Replace with:**
```js
queryClient.invalidateQueries({ queryKey: ['someKey'] });
```
This applies whether the key is a single string in an array (`['products']`) or includes variables (`['product-search', debounced]`, `['sale', id]`) — the array itself doesn't change at all, only how it's passed to `invalidateQueries`. A safe, mechanical find-and-replace across these 17 files: search for `invalidateQueries([` and wrap what follows as `invalidateQueries({ queryKey: [ ... ] })`, closing the extra brace before the final `)`.

### Also fix `UserForm.jsx` — the one file with mutations but zero invalidation at all

This one's a different, smaller gap: it has 2 `useMutation` calls and never invalidates anything, meaning after creating or editing a user, the Users list page won't show the change until a manual refresh, regardless of the invalidateQueries syntax fix. **Find each mutation's `onSuccess`** and add:
```js
onSuccess: () => {
  queryClient.invalidateQueries({ queryKey: ['users'] });
  // ...whatever else the existing onSuccess already does (navigation, toast, etc.) — add this alongside it, don't replace it
},
```
(Confirm `['users']` matches whatever query key `Users.jsx` actually uses for its list — check that file if unsure, don't guess the key.)

### Why this is worth doing as one pass, not page-by-page over time

Every one of these 17 files currently *looks* correct at a glance — the intent is right, the query key is right, it's only the call shape that's wrong. That's exactly the kind of bug that's easy to keep copy-pasting into new pages going forward if it isn't caught and fixed everywhere at once now. Worth telling your coder explicitly: after fixing all 17, re-run the same search (`grep -rn "invalidateQueries(\[" frontend/src`) and confirm it returns nothing, as the actual completion check — not just "I fixed the ones I remembered."

### Acceptance criteria
- After adding a product, the Products list shows it immediately, no refresh needed. Same test repeated for: adding a category, adding a supplier, adding a customer, creating a sale (Sales list updates), creating a purchase, adjusting stock (Products/Inventory reflect the new quantity), creating/editing a user, updating Shop Info, updating Backup Settings.
- The shift indicator from the earlier fix now updates immediately on open/close, not just via the 30-second fallback timer.
